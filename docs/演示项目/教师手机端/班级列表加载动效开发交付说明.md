# 班级列表加载动效开发交付说明

适用页面：教师手机端「班级」「社团与团队」列表。2026-10-22。

## 演示与验收

每次刷新或重新打开演示，默认模拟首次无数据加载1800毫秒，使用三张标准占位卡，数据到达后交接到真实内容。同次打开期间按账号、来源空间、班级／团队页签记录已加载状态；返回已加载列表、切回已加载页签、年级筛选及任教筛选不重播，直接显示内容。未加载过的列表首次进入时各自模拟一次；尚未完成就离开时，不标记为已加载。

手机外侧右上方的「列表加载演示」支持：选择1.8／4.5／8秒模拟等待时间（选择后立即重播）；点击「重播加载」主动绕过已加载记录，重新观察扫光与内容入场；点击「保持骨架」持续观察扫光，随后点击「显示内容」立即交接到真实内容。默认1.8秒仅为模拟首载体验，不是线上等待标准或接口性能指标。控制只出现在班级／团队列表上下文，不放进手机页面，不依赖真实网络限速。

- 白色卡面与屏幕渐变全程保留。骨架与内容共用布局，卡片不缩放、不整体移动。
- 班级按现有标题、关系标签、年级人数、操作区占位，不新增头像；团队显示56像素圆头像、标题、负责人及人数、操作区占位。
- 班级标签与人数统计骨架统一为13像素高，低于班级名骨架的18像素。标签仅绘制一条，不随真实标签数量或换行增高；仅调整骨架图形，保留真实标签与卡片的布局高度。首屏占位和手动演示一致。
- 骨架条长按视觉层级预估，不要求等于真实文字长度：标题骨架保留左侧起点，右边缘对齐同卡片底部右侧按钮骨架的右边缘，与更多操作保留间隔，班级标签与人数信息使用同一内容列宽度的72%，保持等宽；团队内容使用82%。底部操作骨架按两列左对齐：班级第一条与标题、内容对齐；团队第一条与头像左边线对齐，第二条位于右列。团队以含头像的完整内容区域为锚点，排除内边距后平分两列，与班级使用相同可用宽度及78%长度比例，保证同屏宽下按钮骨架等长。以上只改变骨架图形，不移动真实文字、按钮或触控区域。
- 学校班级页年级筛选文字、社团与团队的「我参与的」勾选框及两页「共x个」统一24像素左侧起点，四处共用4像素左内边距。正常态与骨架态一致，保留原触控尺寸及卡片位置，班级卡片内容仍为36像素起点；顶部空间不足时自然换行，排行榜保持右对齐。
- 整个列表共用一层骨架蒙版和一道柔和斜向光带，1500毫秒从左向右循环扫过。
- 数据就绪后，头像、标题、内容、操作区按0／60／120／180毫秒延迟入场，300毫秒内从透明、下方8像素过渡到正常位置。班级没有头像，按标题、标签、元信息、操作区排序。各块对应的骨架同步淡出。
- 保留44像素触控区域；加载时列表卡片不可点击、不可键盘聚焦。减少动态效果时静态占位，数据到达直接展示。
- 数量统计与卡片共用同一骨架蒙版和扫光；加载期间在原文字位置展示短骨架条，保留18像素统计行、原缩进和卡片间距，真实数量原位淡入且不做上移。加载完成且结果为空才显示零值与空态。
- 数量骨架与卡片使用相同浅灰底色和扫光亮度；学校班级与社团团队页「共x个」共用48像素宽、10像素高，不受统计数字位数影响，真实统计文字保持自然宽度；个人班级数量摘要保持原文字测量宽度的120%。左侧起点不变，不增加白色底板。

## 线上接入

### 展示规则

| 场景 | 展示方式 |
| --- | --- |
| 首次请求，无当前列表的有效结果 | 数量与卡片显示骨架，不提前显示零值或空态 |
| 已有非空缓存，后台刷新 | 直接显示缓存及真实数量，保留交互，不展示骨架、不重播入场 |
| 已确认的空结果，后台刷新 | 保留零值和空态，不回退骨架 |
| 返回列表或切换到已加载页签 | 直接显示该列表的有效结果 |
| 首次请求失败 | 结束骨架，接入现有错误反馈与重试；不能误显示为空列表 |
| 刷新失败，仍有有效缓存 | 保留缓存，沿用现有错误反馈，不清空列表 |

数据一到就开始内容交接，不人为延迟、不设置骨架最短展示时间、不等待扫光循环完成。缓存是否可用由数据层判断；账号、来源空间、班级／团队页签必须隔离，不能把上一账号或来源的数据用于当前列表。刷新期间保留最近一次成功结果，更新成功后替换数据；权限变化使缓存失效时应清理对应结果和成功标记。

### 组件与数据契约

1. `mobile-app/components/ui/MobileSkeletonList.tsx` 与同名样式封装通用加载效果。真实内容节点通过 `skeletonBlock` 标注形状及入场顺序，组件按布局坐标生成蒙版；坐标不受演示手机壳缩放影响。
2. `mobile-app/views/ClassListView.tsx` 接收 `loading` 和 `hasLoaded`。前者表示请求中，后者表示当前列表有可用的成功结果，成功返回空数组也必须为 `true`。正式接入须明确传入两项；仅当 `loading && !hasLoaded` 才显示骨架。兼容旧调用时，非空原始数组视为已有内容，但不能用此兼容行为代替空结果标记。按当前页签判断，不使用筛选后的条数推断加载状态。首次请求的初始状态应直接为加载中，避免先出现空态再启动请求。
3. 成功时同次更新数据、`hasLoaded=true`、`loading=false`；后台刷新只更新请求状态，保留数据和成功标记。首次失败不得标记成功，必须由请求层切换到错误与重试视图；刷新失败保留有效的成功结果。当前演示没有接入真实网络与错误视图，不能单独将 `loading=false` 作为首次失败处理，否则会显示空态。
4. 根演示容器 `App.tsx` 持有 `classListLoadingPreview`，经 `mobile-app/App.tsx` 传入 `demoLoadDuration`、`demoLoadKey`、`demoHoldLoading`、`demoInitialLoad`。默认模式为 `timed`、1800毫秒，首轮使用标准无数据占位；`shared/classListLoadingPreview.ts` 的会话记录仅保存在当前页面内存，列表卸载重进仍可复用，刷新或重新打开演示清空。手动重播增加轮次，允许再次观察。当前本地演示数据同步就绪，所以传入 `hasLoaded=true`；开发接线上时必须替换为当前列表的数据状态。正式产品移除手机外调试工具及演示会话逻辑，不传上述演示参数。
5. 首次没有数据时使用 `ClassListLoadingCards` 的三张标准卡，关系标签预留一行长条，不猜测真实标签数。允许无标签、有标签及标签换行卡片在数据到达后自然调整高度，保持标题栏、第一张卡片起点和底部导航稳定，不为骨架强制所有真实卡片等高。仅手动演示时可使用已知内容测量占位；正式有缓存时直接显示内容。
6. 组件使用 `--tm-skeleton-*` 公共令牌维护颜色、扫光周期、入场间隔、持续时间和位移。微信原生小程序需按相同时序、布局和共享蒙版原则实现对应组件。

开发验收应覆盖：无标签／有标签／标签换行，首次慢网、快速返回、首次失败与重试，非空及空结果缓存刷新，刷新失败，切换账号／来源／页签，以及减少动态效果。渲染检查只验证结构和状态分支，实际网络、缓存有效性、失败提示和设备上的布局稳定需接入后验证。

本次交付包含演示样式、缓存优先的展示条件、手动调试入口与接入契约；没有新增真实请求、持久缓存或线上错误处理，也未发布正式产品。由开发接入现有数据层并按上述场景验收后上线。

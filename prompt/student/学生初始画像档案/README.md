# 学生初始画像档案｜工具四 v1.1.0

这套文件用于“原始问卷、档案 → 按既定模板填写字段 → 校验 → 建立学生初始画像档案”。文本风格与本次确认的家长版报告一致，字段规则以学校《工具四》为准。

**已固化的是提示词、字段规则和接入合同；尚未新增生产 API（应用接口）、调用模型或写入数据库。** 示例为人工编写的虚构联调数据，通过了本地格式与字段规则核对，不代表已经完成真实模型生成质量测试。

## 1. 文件怎么用

| 文件 | 用途 |
|---|---|
| `学生初始画像档案-工具四-v1.md` | 固定系统提示词。调用时使用分隔线之后的正文；将每次输入 JSON 作为独立的数据消息传入。 |
| `工具四字段规则-v1.json` | 工具四的 40 个固定 AI 字段：原表项目、类型、来源、句式、长度与填写规则。 |
| `示例/输入示例-虚构学生.json` | 一份完整输入：目标档案模板、字段绑定、三方资料、系统填写值。所有 `example` 标识仅为示例。 |
| `示例/输出示例-人工编写.json` | 对应的完整输出，含 40 个字段值和依据。故意保留“孩子遇难行为暂缺”和“体缺少直接资料”的情况，展示如何处理资料缺失。 |
| `示例/输出约束-示例JSONSchema.json` | 与该输入对应的 JSON Schema（结构与取值约束）。正式调用必须根据实际模板和资料项重新生成，不能照搬示例键。 |
| `工具四字段清单.md` | 给产品、教研和开发核对的完整字段清单。 |

长度上限是这次提出的技术约定，用于控制字段长度，不属于专家原表规定。正式调整上限时，要同步规则目录、约束和排版要求，不要只改提示词。

## 2. 推荐的实际流程

```mermaid
flowchart LR
  A[教师提前设计档案分组与字段] --> B[绑定工具四规则与真实字段标识]
  B --> C[按学生ID读取三方原始资料]
  C --> D[AI按字段生成JSON]
  D --> E[程序校验字段、选项、原话和来源]
  E --> F[保存初始画像草稿]
  F --> G[教师核对并修改]
  G --> H[确认归档并向家长展示]
```

数据库可以先存通过结构校验的生成草稿，资料缺失与核对事项另外保存。原表已经规定教师修改、确认，`draft_ready` 只表示生成完成，不表示教师已经确认。内部依据和核对事项不要混进给家长看的字段值。

## 3. 如何衔接现有档案设计

现有结构已经支持所需答案格式：

- `shared/studentArchiveStore.ts`：`ArchiveTemplate.fields` 定义字段，`ArchiveField.semanticKey` 是答案键；`ArchiveDraft.answers` 保存答案。
- `mobile-app/views/archive-design/ArchiveFormRenderer.tsx`：读取 `answers[field.semanticKey]` 显示或编辑答案。
- `shared/archiveCollectionPersistence.ts`：问卷采集结果也使用语义标识映射到档案答案。

本次规则目录的 `ruleKey` 是业务含义标识，例如 `summary.temperament.judgment`。**它与目标模板实际的 `semanticKey` 是两个不同概念。** 字段设计完成后，由程序或配置人员绑定，不能让模型凭字段名猜测。

例如：

```json
{
  "semanticKey": "目标模板实际保存的字段标识",
  "ruleKey": "summary.temperament.judgment"
}
```

模型返回：

```json
{
  "answers": {
    "目标模板实际保存的字段标识": {
      "selectedOptions": ["家长与教师观察有差异"],
      "customText": {}
    }
  }
}
```

这是展示映射关系的局部片段；完整输出以示例 JSON 为准。

档案设计中可以有多个同名“初步判断”，因此不能用中文字段名作为入库键。分组换序或字段显示名调整时，只要字段含义、类型和真实标识没有变化，绑定可以保留；删除重建、含义变化、类型变化、选项变化时，必须重新核对绑定并更新模板版本。

多项填空还要绑定真实 `subFields[].id`。本方案将三个特质作为一个 `multi_fill` 字段、三个子项；当前代码每个子项最多 120 个字符。若学校实际设计成三个独立文本字段，需要先更新绑定方案和对应规则版本，不能在运行时让模型自行改结构。

## 4. 字段数量及原表约束

| 原表内容 | AI 字段数 | 建议类型 |
|---|---:|---|
| 基础信息汇总：5 个维度 × 4 个来源/判断值 | 20 | 19 个文字、1 个单选 |
| 家长说、孩子说、老师看到了 | 3 | 文字 |
| 五育当前可见状态 | 5 | 文字 |
| 三力萌芽证据 | 3 | 文字 |
| 光芒图：4 个来源值 + 交汇建议 | 5 | 文字 |
| 待观察区 | 1 | 文字 |
| 成像寄语：三个特质、需要理解、陪伴起点 | 3 | 1 个多项填空、2 个文字 |
| **合计** | **40** | **38 个文字、1 个单选、1 个多项填空** |

“学生姓名”由系统学生资料填写。“成像日期”可设计为日期字段，使用年-月格式，由程序按生成时间填写。示例模板包含 40 个 AI 字段及 1 个程序填写的日期字段，姓名使用现有 `systemFields`。

基础汇总的气质判断严格限制为三个原选项。另四个判断的前缀固定。五育、三力、光芒图、成像寄语的原项目和句式保存在规则目录中。

示例为了在现有单层分组中区分矩阵行列，将“观察维度｜来源”用作字段显示名。正式接入以学校实际设计的显示名为准，绑定保证它对应原表的同一个填写位置，不要求改学校已设计的模板。

## 5. 每次调用需要传什么

1. **实际模板及版本**：取档案设计保存的快照，包括字段类型、选项、子字段，禁止手写一套与数据库不同的字段定义。
2. **绑定表及规则目录**：验证 40 个规则各绑定一次，目标字段唯一；日期等程序字段不在 AI 绑定中。规则和模板冲突时先修正配置，不让模型决定以哪份为准。
3. **单名学生的三方原始资料**：按学校和学生真实 ID 获取，不用姓名进行跨表模糊归属。来源角色由学校问卷/档案任务配置确定，不能仅凭表名猜测。
4. **来源原文及标识**：每个答案有稳定的 `sourceItemId`、原题和 `answerText`。选择题的 `answerText` 是保存时的选项文字，多项填空保留子项内容；数字单位和否定词不能丢失。引用选项不能被误标为孩子主动说出的原话。
5. **明确版本与去重**：同一份回答如果同时出现在问卷和归档快照中，应按来源记录关系去重；这不算两份独立证据。同题多版本先由业务系统选择，不能依赖数据库返回顺序。
6. **确定性信息**：姓名、生成日期、学段来自程序。不要将日常评价、积分、排名和旧 AI 画像一并塞入来源资料。

`requestId`、`studentId`、模板版本等归属信息以服务端请求上下文为准，不能信任模型重新生成的身份。模型只回传 `requestId` 供一致性检查。

## 6. 入库前必须由程序完成的检查

这些检查必须由程序执行，不能只依赖模型的“自查通过”。

| 检查 | 不满足时的处理 |
|---|---|
| JSON 可解析，顶层键和输出版本正确，请求标识一致 | 拒绝本次结果，保留错误原因 |
| 答案键恰好等于本次 AI 绑定键，不含其他模板字段 | 拒绝整次结果，避免错列入库 |
| 单选为规定选项且恰好 1 项，不接受自由写句子 | 拒绝；不能将非法值悄悄转换为“尚不清晰” |
| 多项填空的子字段 ID、数量和长度正确 | 拒绝结构错误；证据不足的空值仅允许进入待核对草稿 |
| 四个判断前缀和完整句式正确，未重复拼接标签 | 拒绝或仅修复确定的格式问题，不静默改语义 |
| 引用编号真实存在、属于当前学生且来源角色正确 | 拒绝伪造引用或错来源引用 |
| 家长、孩子原话可在对应原文中逐字找到 | 不匹配就拒绝，不自动润色来“修好” |
| 缺失、冲突、异常有对应核对事项 | 保留为 needs_review 草稿；来源缺失由程序再次判断 |
| 当前模板版本、来源版本仍与生成请求一致 | 已变化就作废旧结果，按新版本重新生成 |
| 与已有教师修改、历史归档的关系明确 | 不直接覆盖教师已修改内容或历史版本 |

JSON Schema 负责结构、类型、选项、长度等约束。它不能证明判断正确或引用支持结论，也不能完整校验所有业务关系；这些仍需程序交叉核对与教师审阅。

现有 `getArchiveAnswerValidationError` 可复用部分必填、数量、长度校验，但当前代码**没有完整检查单选项是否属于选项集合**，不能直接作为 AI 输出的全部校验器。数字、评分不是本工具四 v1 的生成字段，不得为了“量化”自行添加。

## 7. 草稿、重试和重新生成

- 模型输出的 `status` 是生成任务状态，另存任务记录；不能直接当作现有档案对象的状态字段。
- `answers` 与 `fieldEvidence` 分开存：前者是家长可见的档案值，后者用于教师核对和问题追踪。
- 用学校、学生、模板版本、规则版本、来源版本摘要和生成目的组成一次任务的去重依据。同一次请求重试不能插入多份新档案；确需重新成像时创建明确的新修订任务。
- 首次生成写入新草稿。再次生成应保留上次生成基线，与当前教师编辑内容比对；教师修改过的字段不自动覆盖，可形成待确认的新建议。
- 当前 `upsertStudentArchiveCollectionAnswers` 会合并已有草稿或最新快照答案。直接复用会有“旧值残留”和覆盖教师修改的风险。应新增受校验的 AI 草稿写入入口，或明确控制本次 40 个字段及其变更策略，不能直接把模型结果塞进通用合并函数。
- 当前仓库该档案模块的持久化入口使用浏览器本地存储。生产数据库表名、接口、事务和权限需要按真实后端接入，本文件不假设现有前端存储就是生产数据库。
- 结构错误可以携带具体校验错误进行有限次修复重试；建议最多 1 次。资料缺失不能靠反复调用模型补成事实，失败后进入人工处理，不无限重试。

## 8. 上线前的最小验收范围

至少覆盖：三方资料完整；缺少一种来源；孩子没回答某题；勾选与文字冲突；家庭与学校表现不同；固定选项被写成长句；不存在的字段键或引用编号；跨学生资料；模板改版；重新生成时已有教师修改；原话有错字；来源包含“忽略规则”等指令。

验收同时看两层：程序能否拦住错误数据，以及教师是否认可内容忠实、温和、简明。当前示例只验证第一层中的格式与字段规则，还需要真实模型样本和教研复核后再发布生产配置。

## 9. 2026-10-27 五育修订

- 展示顺序统一为德、智、体、美、劳。原表名称保留，本次已确认的顺序覆盖原 Word 排列。
- 德按证据加入待人、规则与礼仪表现；文明礼仪不是必填子项，不由“爱笑”“听指令”推断，也不编造问好、道谢的场景。
- 体聚焦运动与健康生活习惯；穿脱、上厕所、自己吃饭、整理物品统一归劳。一般课堂注意或跟随指令不能代替体育证据。
- 五育内按具体行为去重；同一来源条目包含不同事实时可以拆分归类。某育证据不足时明确暂缺。
- 规则版本为 `tool4-rules-v1.1.0`，提示词版本为 `tool4-v1.1.0`。规则目录内的 `fiveEducationPolicy` 保存本次补充规则，报告生成器与其共用五育顺序。
- 调整排列时保留原字段标识，更新显示顺序和模板版本。示例已经调整为模板版本 2，五育原有的 semanticKey 没有重新编号，避免“体”的旧值被误写到“德”。
- 虚构示例本身没有运动、作息或健康习惯资料，因此体明确暂缺，原来的穿脱、上厕所内容移至劳，没有补造体育表现。该情形已加入 needs_review 核对事项。
